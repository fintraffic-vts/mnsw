S2S Quickstart: call the API in 5 minutes

Authenticate, validate a payload against EMSA MIG, and submit your first formality to Finland's Maritime Single Window.

Prerequisites

  • Issued client_id and client_secret (request via onboarding and access), and your organizationBusinessId.
  • Network egress to the selected environment and token endpoint (provided during onboarding).
  • Tooling: curl or Postman, and a JSON editor/validator.

Environments

External users: STG and PRD only. DEV/TST are internal to the MNSW team.

EnvironmentBase URLAuthenticationNotes
STGhttps://mnsw-stg.mnsw.fi/OAuth2 client credentialsActive
PRDhttps://mnsw.mnsw.fi/OAuth2 client credentialsOnboarding required

The exact issuer and token URL are shared during onboarding. Replace <TOKEN_URL> in examples accordingly.

Architecture at a glance

  1. 1Your system

    Requests a token with OAuth2 client credentials.

  2. 2Keycloak

    Returns an access token (JWT).

  3. 3National API

    Accepts authorized port-call and formality requests.

  4. 4MIG schema

    Validate the formality payload before sending it.

Step-by-step

1) Get an access token

Use the client issued for your organization (declarant or port) with the OAuth2 Client Credentials grant. The flow is identical for both.

  • STG: https://mnsw-stg.mnsw.fi/keycloak/realms/nemo/protocol/openid-connect/token
  • PRD: https://mnsw.mnsw.fi/keycloak/realms/nemo/protocol/openid-connect/token

Only STG and PRD are supported for external integrators. DEV/TST are for the MNSW team only.

ENV=stg   # or prd
case "$ENV" in
  stg) IDP_HOST=mnsw-stg.mnsw.fi/keycloak ;;
  prd) IDP_HOST=mnsw.mnsw.fi/keycloak ;;
  *) echo "Use stg or prd (DEV/TST are internal)"; exit 1 ;;
esac

TOKEN_URL="https://$IDP_HOST/realms/nemo/protocol/openid-connect/token"
CLIENT_ID=<client_id>
CLIENT_SECRET=<secret>

ACCESS_TOKEN=$(curl --fail-with-body -sS -X POST "$TOKEN_URL" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=client_credentials" \
  -d "client_id=$CLIENT_ID" \
  -d "client_secret=$CLIENT_SECRET" | jq -er '.access_token // empty')

Keep client secrets and access tokens out of source control, logs, and shared messages. Send the access token using the standard OAuth2 authorization scheme, together with the organizationBusinessId header.

2) Smoke test your token

Call an authorized endpoint to verify the token and organization header:

export BASE=https://mnsw-stg.mnsw.fi
export ACCESS_TOKEN=<access_token>
export ORG_BID=<your_organizationBusinessId>

curl -i "$BASE/nemo-ui/api/v1/codelists/names" \
  --oauth2-bearer "$ACCESS_TOKEN" \
  -H "organizationBusinessId: $ORG_BID"

3) Build a minimal formality payload

Start from the EMSA MIG JSON Schema for the formality type (for example NOA, NOD, or CGD), populate required fields, and follow national rules where applicable.

Preparing a valid NOA payload

Use the exact envelope, element names, and namespaces from the NOA JSON Schema. Save the complete, validated document as payload.json; a simplified illustrative object is not a valid submission.

MIG-P33 — Unknown data: if an optional element's value is unknown, omit it. Do not send empty strings, 0, or null.

4) Submit the formality

Submit to the Declarant API endpoint for the port call. The API accepts formalityData as an application/json multipart field. Use the formality ID when updating an existing formality.

export VISIT_ID=<portcall-visitId>
export FORM_TYPE=NOA  # e.g., NOA, NOD, CGA, CGD, ATA, ATD
export FORM_ID=<stable-formality-uuid>

curl -i -X POST "$BASE/declarant-api/v1/portcalls/$VISIT_ID/formalities/$FORM_TYPE" \
  --oauth2-bearer "$ACCESS_TOKEN" \
  -H "organizationBusinessId: $ORG_BID" \
  -F "formalityData=@payload.json;type=application/json"

# Update the same formality later:
curl -i -X PUT "$BASE/declarant-api/v1/portcalls/$VISIT_ID/formalities/$FORM_TYPE/$FORM_ID" \
  --oauth2-bearer "$ACCESS_TOKEN" \
  -H "organizationBusinessId: $ORG_BID" \
  -F "formalityData=@payload.json;type=application/json"

5) Validate and troubleshoot

  • Validate JSON against the MIG 2.0.1.0 schema for the formality type.
  • For 4xx errors, check the response body for EMSA MIG or national-rule validation errors.
  • Include the request-id (if returned in headers or body) when contacting support.
Alternative channel: AS4 (RIM/Domibus)

If you integrate via AS4, package the same MIG payload as the business document and send it via Domibus/RIM. Error semantics mirror REST responses.

  1. 1Your back office

    Packages the business document.

  2. 2Domibus/RIM

    Delivers the AS4 message.

  3. 3MNSW Core

    Processes the message and returns acknowledgements.

FAQ

What scopes or claims are required?

Scopes are provisioned with your client during onboarding. Always include the organizationBusinessId header matching your organization.

How do I find the right schema version?

Use the MIG 2.0.1.0 schemas published by the NEMO Developer Hub. For breaking changes, see the Changelog.

Ilmoittajan API

API:n avulla ilmoittaja voi hallita satamakäyntejä ja niihin liittyviä ilmoituksia.

Avaa täydellinen OpenAPI-dokumentaatio
  • GET /v1/portcallsHae ilmoittajan satamakäyntejä.
  • POST /v1/portcallsLuo uusi satamakäynti.
  • GET /v1/portcalls/{visitId}/formalitiesHae satamakäynnin ilmoitukset.
  • POST /v1/portcalls/{visitId}/formalities/{formalityType}Luo ilmoitus satamakäynnille.
  • PUT /v1/portcalls/{visitId}/formalities/{formalityType}/{formalityId}Päivitä tai peruuta olemassa oleva ilmoitus.
Sataman API

Sataman API tarjoaa satamatietoja ja alusten tietoja sekä vastaanottaa satamatilastoja.

Avaa täydellinen OpenAPI-dokumentaatio
  • GET /v1/ports/dataHae satamatietoja.
  • POST /v1/ports/statisticsLähetä satamatilastoja.
  • GET /v1/shipsHae alusten tietoja ja niihin liittyviä todistuksia.
  • GET /v1/ships/identifiersHae alusten tunnisteita.
Sijaintitietopalvelun API

OpenAPI-kuvauksen perusteella palvelusta voi hakea sijaintitietoja, Suomen satama-alueita ja laituripaikkoja sekä GISIS-koodeja.

Avaa täydellinen OpenAPI-dokumentaatio
  • POST /api/v1/locationHae sijainteja nimen tai LOCODE-tunnuksen perusteella.
  • GET /api/v1/location/locodesHae saatavilla olevat LOCODE-tunnukset tai suodata niitä tunnuksella.
  • GET /api/v1/location/locodeCheckTarkista, löytyykö LOCODE palvelusta.
  • GET /api/v1/nationalPortAreaHae Suomen satama-alueita LOCODE-tunnuksen perusteella.
  • GET /api/v1/nationalBerth/listByPortAreaCodeHae laituripaikkoja satama-alueen koodilla.
  • GET /api/v1/nationalBerth/listByGisisCodeHae laituripaikkoja GISIS-koodilla.
  • GET /api/v1/nationalBerth/{code}Hae laituripaikan tiedot sen koodilla.
  • GET /api/v1/gisisHae GISIS-koodeja LOCODE-tunnuksella tai kaikki saatavilla olevat koodit.

Tarkista tunnistautumisvaatimukset, osoitteet ja käyttöoikeudet palvelun OpenAPI-kuvauksesta.

AS4-viestivirta: neljän kulman malli

Lähettäjä hallitsee omaa taustajärjestelmäänsä ja AS4-yhteyspistettään. RIM vastaanottaa viestin, tarkistaa lähettäjän rekisteröinnin ja välittää sen kansalliseen käsittelyyn.

  1. 1Lähettäjän järjestelmä · C1

    Muodostaa ilmoituksen ja ASiC-E-sanomasäiliön.

  2. 2Lähettäjän AS4-yhteyspiste · C2

    Allekirjoittaa ja salaa AS4-viestin sovitun profiilin mukaisesti.

  3. 3Suomen RIM · C3

    Vastaanottaa viestin, tarkistaa valtuutuksen ja reitittää aineiston.

  4. 4NEMO · C4

    Käsittelee ilmoituksen kansallisten sääntöjen mukaisesti.

Viestikuittaus palautuu AS4-vastauksena. RIM voi myös lähettää teknisen tai liiketoiminnallisen vastauksen lähettäjän AS4-yhteyspisteeseen.

Käyttöönotto ja ympäristöt

  1. Sovi integraatiopolku

    Varmista, mitä API:a tai AS4/RIM-yhteyttä käyttötapauksesi edellyttää, ja pyydä tarvittavat tunnukset ja roolit.

  2. Valmistele lähettäjän tiedot

    AS4-polulla varmista lähettäjän tunnisteet, EORI, yhteyspiste, verkko-osoitteet ja varmenteiden vaihto. URAM-rekisteröinnin on vastattava viestin tietoja.

  3. Testaa vaiheittain

    Aloita sovitussa testiympäristössä, varmista tekninen viestinvaihto ja päästä päästä -toiminta ennen staging- ja tuotantosiirtymää.

  4. Koordinoi muutokset

    Ilmoita etukäteen endpoint-, avain-, varmenne- tai IP-osoitemuutoksista; päivitä asetukset ja testaa ennen tuotantoaktivointia.

Ympäristöjen osoitteet, tunnisteet, varmenteet ja muut sopimusarvot vahvistetaan käyttöönotossa. Älä kopioi esimerkkiasetuksia tuotantoon sellaisenaan.

Ympäristöt integraatiopolun mukaan

Ympäristöjen järjestys riippuu valitusta tiedonsiirtotavasta. Käytä aina kyseisen rajapinnan tai AS4-yhteyden ohjeissa vahvistettuja osoitteita ja tunnuksia.

Tietoturva ja varmenteet

Ilmoituksen allekirjoitus

AS4-polulla C1 allekirjoittaa ASiC-E-sanomasäiliön eIDAS QES- tai AdES-allekirjoituksella. Allekirjoitus on erillinen AS4-yhteyspisteen viestiallekirjoituksesta.

AS4 ja TLS

C2:n X.509-varmenteita käytetään AS4-viestin allekirjoitukseen ja salaukseen. TLS suojaa verkkoyhteyden yhteyspisteiden välillä; luottamusketjut on asennettava sovitusti.

Tunnistaminen ja valtuutus

AS4-viestien lähettäjän tiedot tarkistetaan URAM-rekisteröintiä vasten, mukaan lukien EORI. API-käytössä käytetään myönnettyjä OAuth2 client credentials -tunnuksia.

Avainten käsittely

Säilytä yksityiset avaimet ja API-salaisuudet vain suojatuissa avain- ja salaisuusholveissa. Älä jaa niitä lokien, tikettien tai koodivarastojen kautta.

Seuranta, virhetilanteet ja tuki

Seuraa yhteyden toimintaa

  • Lähetettyjen ja epäonnistuneiden viestien määrä sekä käsittelyjonojen kasvu.
  • AS4-kuittausten ja RIM-vastausten saapuminen sekä vastausten kohdistuminen alkuperäiseen viestiin.
  • Yhteyspisteen HTTPS-saatavuus ja varmenteiden voimassaolo.
  • Ympäristökohtaisten endpoint-, tunniste- ja tietoturva-asetusten vastaavuus.

Kun viesti epäonnistuu

Tarkista vastaanottokuittaus, vastaussanoma, MessageId, lähettäjän rekisteröintitiedot sekä käytössä olevan ympäristön PMode- ja varmenneasetukset.

Tukipyynnössä ilmoita ympäristö, ajankohta ja MessageId. Älä liitä pyyntöön salasanoja, yksityisiä avaimia tai tarpeettomia henkilötietoja.
